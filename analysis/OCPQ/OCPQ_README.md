# OCPQ Reproduction Package — CSQ1 to CSQ3

This directory contains the OCPQ-based reproduction materials for the first three case-study questions (CSQ1–CSQ3) reported in the thesis **Design for Simulation in Object-Centric Process Management**.

The package preserves both:

1. the **OCPQ query definitions and raw exports** used in the thesis; and
2. the **Python analysis scripts and generated outputs** used to reproduce the reported tables and figures.

The analyses are based on the preserved **baseline simulation Run 1**. The reported numerical results describe the behaviour generated by that configured simulation run; they are **not empirical estimates of real organisational performance**.

---

## 1. Scope and thesis mapping

### CSQ1 — Baseline performance

> How long does a submitted Requirement that reaches accounting-voucher posting take to do so, and how is this elapsed time distributed across process stages in terms of contribution and variability?

Current thesis outputs:

- **Figure 4.2** — OCPQ path and throughput-time distribution from Requirement submission to accounting-voucher posting.
- **Table 4.9** — stage-level decomposition of simulated submission-to-posting elapsed time.
- **Figure 4.3** — distribution of the four stage durations for the 25 posted Requirements.

### CSQ2 — Long-tail diagnosis

> Among Requirements that reach accounting-voucher posting, which observed rework and routing characteristics are associated with unusually long submission-to-posting times?

Current thesis outputs:

- **Table 4.10** — observed rework and routing characteristics of upper-tail and remaining posted Requirements.
- **Table 4.11** — acceptance-rework depth and realised elapsed time among posted Requirements.

### CSQ3 — Synchronisation and post-readiness accounting delay

> How much simulated synchronisation delay occurs between invoice receipt and asset readiness, and how much additional time elapses from asset readiness to accounting-voucher posting?

Current thesis outputs:

- **Figure 4.4** — OCPQ query binding Invoice and Asset prerequisite/accounting events.
- **Table 4.12** — accounting-synchronisation and post-readiness results.
- **Figure 4.5** — distribution of post-readiness elapsed time.

## 4. Two reproduction levels

Two levels of reproduction are supported.

### A. Reproduce the thesis statistics from the preserved OCPQ exports

This is the shortest and most deterministic route.

The raw OCPQ CSV exports and query JSON files are already preserved in the repository. Run the Python scripts as described in Sections 6–8 below. The scripts read the raw OCPQ exports directly, regenerate the intermediate/result files, and assert the baseline values reported in the thesis.

### B. Re-execute the OCPQ queries from the Run-1 OCEL

This route additionally reconstructs the OCPQ query layer.

1. Open the preserved baseline Run-1 OCEL in **OCPQ Desktop v0.11.2**.
2. Restore or recreate the relevant query using the preserved `.json` file and the corresponding `*_query_definition.md`.
3. Evaluate the query in OCPQ.
4. Export the resulting Situation Table or Path Schema connections as CSV.
5. Save the export under the filename documented below.
6. Do **not** manually edit, reorder, normalise, or round the raw export before running the Python analysis.
7. Run the corresponding Python script.

For ordinary OCPQ query JSON files, the preserved query can be restored by copying the complete JSON text and pasting it into an empty OCPQ query canvas. Exact query variables, constraints, labels, and expected result sizes are documented in each `*_query_definition.md`.

### Important CSQ1 Path Schema note

`csq1_path_query.json` is the preserved **Open as Query** representation of the selected path; it is not a complete serialization of all Path Schema GUI settings.

To reconstruct the Path Schema used for Figure 4.2, use the settings documented in `csq1_query_definition.md`, including:

```text
Source event:      Submit Requirement
Target event:      Post Accounting Voucher
Maximum K:         2
Temporal direction: Forward
Selection:         All
```

The preserved raw Path Schema evidence is:

```text
csq1_path_connections.csv
csq1_path_schema_overview.png
csq1_path_throughput_results.png
```

## 5. General file roles

The files in each CSQ folder have different roles.

| File type | Role |
|---|---|
| `*_query.json` | Machine-readable OCPQ query definition or preserved Open-as-Query representation |
| `*_query_definition.md` | Human-readable documentation of variables, constraints, operationalisation, expected counts, and thesis mapping |
| `*_situation_table.csv` | Raw OCPQ export; treated as an input and preserved without manual editing |
| `*_connections.csv` | Raw OCPQ Path Schema connection export |
| `*_analysis.py` | Reproduction script that performs calculations, cross-checks, and baseline assertions |
| `intermediate/` | Generated row-level or cross-check data |
| `results/` | Generated thesis tables, figures, and run summaries |
| `.png` query/path screenshots | Human-readable visual evidence of the OCPQ configuration/results |

For formal baseline reproduction, do not use the `--skip-checkpoints` option. A successful baseline run should end with:

```text
Thesis checkpoint status: PASS
```

## 6. Reproduce CSQ1

Change to:

```text

```

Run:

```bash
python csq1_analysis.py "csq1_milestone_situation_table.csv" --path-connections-csv "csq1_path_connections.csv" --out-dir .
```

The Path Schema CSV is included in the formal command because it independently cross-checks the milestone-query end-to-end duration.

The script verifies, among other checks:

```text
25 satisfied posted-Requirement bindings
25 unique Requirement IDs
S1 + S2 + S3 + S4 = E2E for every Requirement
all required durations are present and non-negative
all 25 milestone rows match the Path Schema source/target event IDs
Path Schema throughput = milestone-query E2E duration row by row
```

## 7. Reproduce CSQ2

CSQ2 uses the same 25 posted Requirements established by CSQ1. It recomputes the empirical 75th percentile (P75) from the full-precision CSQ1 end-to-end durations and then joins OCPQ positive-occurrence results for four lifecycle characteristics.

Change to:

```text
analysis/OCPQ/csq2/
```

Run:

```bash
python csq2_analysis.py "csq1_case_level.csv" "csq2_requirement_modification_situation_table.csv" "csq2_acceptance_rework_situation_table.csv" "csq2_contract_review_situation_table.csv" "csq2_requirement_voucher_mapping.csv" "csq3_voucher_rework_situation_table.csv" --out-dir .
```

The feature-query Situation Tables contain **positive occurrences**, not the full cohort. The script therefore counts positive occurrences and left-joins them to the complete 25-row CSQ1 cohort; unmatched Requirements receive a feature count of zero.

Acceptance rework is operationalised by the preserved OCPQ query as:

```text
Perform Business And Technical Acceptance
where decision = ACCEPTANCE_REWORK
```

Each such decision triggers the corresponding rectify-and-redeliver loop in the implemented model.


The main OCPQ query retains Invoice and Asset as separate object types and derives:

```text
t_ready = max(t_invoice, t_asset)
d_sync = abs(t_invoice - t_asset)

ready_to_verify = t_verify - t_ready
ready_to_post   = t_post - t_ready
```

The voucher-rework query provides an independent cross-check for the three 79-minute post-readiness observations.

## 9. Recommended execution order

For a complete CSQ1–CSQ3 downstream reproduction, run the analyses in this order:

```text
1. CSQ1
   ↓
   generates csq1_case_level.csv

2. CSQ3
   ↓
   independently verifies the voucher-rework rows

3. CSQ2
   ↓
   uses a frozen CSQ1 case-level input and the CSQ3 voucher-rework export
```

With the current repository layout, the frozen upstream files required by CSQ2 are already present in `csq2/`, so each CSQ can also be rerun independently.

If CSQ1 or CSQ3 is regenerated, copy the regenerated upstream file into `csq2/` only after confirming that it matches the preserved baseline version.

## 12. Interpretation and evidence boundary

The OCPQ analyses are part of the thesis **case-study demonstration**.

They establish that the generated Run-1 OCEL preserves the object identities, relations, event ordering, timing, and rework information required to conduct the documented object-aware analyses.

They do **not** establish:

- that the simulation parameters are empirically calibrated to the real organisation;
- that one realised stochastic run provides robust performance estimates;
- that the reported associations are causal effects;
- that the numerical results generalise beyond the configured baseline scenario; or
- that the requirement catalogue is complete or universally valid.

Repeated simulation experiments would be necessary for claims concerning robustness, uncertainty, sensitivity, or comparative performance across alternative simulation scenarios.
